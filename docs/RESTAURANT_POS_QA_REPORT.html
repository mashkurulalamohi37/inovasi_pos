Restaurant POS — Test Execution & Defect Register

Static, unit, and integration testing of the restaurant vertical in omni-pos-core: order lifecycle, table management, KOT/KDS, and billing. Browser-based testing could not be executed — the module does not compile.

Branch main @ 7847be6 Date 2026-08-09 Scope Restaurant vertical only Defects 28
Release verdict
Blocked

Two independent blockers stop the restaurant POS from shipping. The production build fails outright: RestaurantPos.tsx contains a duplicated JSX block committed to main, so neither tsc nor vite build can parse it.

Separately, the billing endpoint rejects every restaurant payment with 400 price_override_reason required. The project's own backend tests confirm it — an order can be taken, sent to the kitchen, and served, but never closed, leaving the table occupied permanently.

Status update. This register records the findings as they stood at main @ 7847be6. All 28 defects have since been fixed — see Remediation for the design decisions worth reviewing and what still needs browser verification.

BUG-01 Critical Duplicated JSX block breaks the build — app does not compile
Repro
  1. Check out main at 7847be6
  2. Run npm run build (or npx tsc --noEmit)
ExpectedBuild completes; bundle emitted.
ActualBuild fails: Expected `}` but found `const` at RestaurantPos.tsx:900:17. tsc reports 15 parse errors. A ~320-line block (product card renderer, modifier / move / split / pay / KOT dialogs) was pasted into the middle of the Kitchen-tickets dialog at line 900, orphaning the original.
ImpactNothing deploys. The restaurant POS route cannot render in any browser, which blocks all nine browser-dependent test cases.
Sourcesrc/features/pos/RestaurantPos.tsx:883–1220
FixDelete the duplicated region (lines 900–1101 re-run content from 703–899) and restore the Kitchen-tickets dialog's original closing tags. Add tsc --noEmit to CI so a non-compiling commit cannot reach main.
BUG-02 Critical Restaurant orders can never be paid — MSP guard rejects every bill
Repro
  1. Open a dine-in order and add a menu item
  2. POST /industry/restaurant/orders/{id}/pay with {"tender":"cash","tax_rate":0.05}
Expected200 — invoice created, order paid, table released.
Actual400 price_override_reason required when selling below MSP or over discount cap. Reproduced by the project's own suite: test_pay_order_creates_invoice_and_releases_table and test_split_payment_equal both fail (2 failed, 10 passed).
CauseThe pricing-authority guard in sales_policy_service.py was widened from fashion-only to all packs, but bill_and_pay_order was never updated. It forwards the menu price as unit_price and builds a meta dict with no price_override_reason key, so any menu price under the product's list price or MSP is rejected.
ImpactHighest-severity operational failure for a restaurant: staff can seat guests, fire the kitchen, and serve food, then find the bill uncloseable. The table stays occupied with no UI path to recover.
Sourcebackend/app/services/restaurant_service.py:892–908 · sales_policy_service.py:185–210
FixTreat the restaurant menu price as authoritative — pass the resolved list price, or thread an explicit price_override_reason through SaleLineIn.meta when the pack is restaurant. Add a regression test that pays an order whose menu price is below base_price.
BUG-03 High Settle Bill dialog understates the amount due by 15.5%
Repro
  1. Build an order totalling ৳1,000 subtotal
  2. Open Bill & Pay and read the dialog
ExpectedVAT + service shown; Total Amount Due ৳1,155.
ActualVAT (5%) + Service shows ৳0 and Total Amount Due shows ৳1,000. order.tax and order.service_charge both default to 0 and are only written during bill_and_pay_order — so the dialog reads them before they exist.
ImpactThe cashier reads ৳1,000 to the guest and the "Exact" preset tenders ৳1,000, while the invoice records ৳1,155. Every dine-in transaction under-collects, and the drawer will not reconcile.
Sourcesrc/features/pos/RestaurantPos.tsx:829–836
FixCompute the preview client-side with the same formula the backend uses — service = subtotal × servicePct, tax = (subtotal + service) × 0.05 — or add a POST /orders/{id}/quote endpoint so the dialog and the invoice share one source of truth.
BUG-04 High Cart total applies tax flat where the backend compounds it
ReproEnable restaurant.service_charge; compare the PosShell cart total to the issued invoice.
ExpectedCart total equals invoice total.
ActualPosShell receives taxRate = 0.10 + 0.05 = 0.15 and renders subtotal × 1.15. The backend charges VAT on the service charge: (subtotal × 1.10) × 1.05 = subtotal × 1.155. A ৳1,000 order differs by ৳5.
ImpactPersistent small variance on every serviced order; compounds across a shift and breaks end-of-day reconciliation.
Sourcesrc/features/pos/RestaurantPos.tsx:484 · restaurant_service.py:920–927
FixPass the service charge to PosShell as a separate line rather than folding it into taxRate, so the display mirrors the backend's order of operations.

04Coverage gaps

  • No browser verification was possible. Cross-browser rendering, viewport behaviour at 390/768/1440px, keyboard navigation, focus trapping, console errors, and back-button-after-logout all remain untested until BUG-01 lands.
  • End-to-end coverage is one assertion. The only restaurant case in e2e/ is GET /restaurant/tables asserting [200, 404] — a 404 counts as a pass. Nothing exercises order → KOT → pay.
  • Table CRUD has zero backend tests. Create, update, and delete are entirely uncovered, which is how BUG-07's AttributeError shipped.
  • No concurrency or load testing. BUG-08 and BUG-27 were found by reading; neither would surface in single-threaded tests.
  • Offline and slow-network behaviour untested. A POS must degrade gracefully; there is no retry, queue, or offline indicator on the restaurant path.
  • Printing untested. KOT printing and receipt output were out of reach without a running app.

05Recommended sequence

  1. Repair the build (BUG-01) and add tsc --noEmit to CI. Everything else is gated on this.
  2. Unblock payment (BUG-02). Until this lands the vertical has no complete happy path.
  3. Reconcile the money (BUG-03, BUG-04) so the dialog, the cart, and the invoice agree to the paisa.
  4. Fix the four API contract breaks (BUG-05, 06, 07, 09) — ideally by introducing typed request models, which closes BUG-20 and BUG-26 as well.
  5. Re-run this plan in a browser. The nine blocked cases plus regression across all 25 executed cases.
  6. Close the test gap (BUG-28) with a real render test and a Playwright spec covering the full service cycle.

06Remediation

All 28 defects fixed. The decisions below changed behaviour beyond a straight repair and are worth a review.

DefectApproach taken
BUG-01Removed lines 900–1094 of RestaurantPos.tsx, a duplicated region re-running 703–899. The 154 type errors this exposed were always present — TypeScript skips semantic checks on a file with syntax errors.
BUG-02Moved the pricing-authority check from settlement to order entry, where staff can still act on it. Added restaurant_order_line.price_override_reason (migration 047) so an approval given at entry is replayed at settlement rather than re-challenging a bill for food already eaten.
BUG-03/04Extracted the bill formula into restaurant-billing.ts and unit-tested it. Service charge and VAT compound (×1.155); they do not add (×1.15).
BUG-08Replaced len(rows) + 1 with the atomic NumberSeries UPDATE already used by sales_service._next_invoice_number.
BUG-09Rates now come from store policy. Undercutting them, setting an explicit tax, or using allow_due requires an override permission — the new restaurant.allow_due.
BUG-10Dropped the .* regex. A wildcard now forces allow_credentials=False, and the wildcard ban extends to staging.
BUG-28Replaced readFileSync substring assertions with 9 behavioural tests that import the code under test.
